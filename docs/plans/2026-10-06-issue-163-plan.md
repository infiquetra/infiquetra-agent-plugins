# Plan review in one pass (issue #163)

## Summary

Replace the plan-review repair loop with one pass: `/plan` dispatches the plan reviewer once, a new script stores the findings as C1 finding records in the run record and gates on every finding answered plus the acceptance-criteria mapping, and `/work` blocks on that check. The cycle allowances, the re-dispatch, the reviewer's in-place edits, the cross-family seat, the second opinion and the one-word override go; rejections are listed, never gating.

---

## Problem Frame

This is card C12 of the saga review redesign (parent issue #147). It changes the gate between planning and building for every run, and that gate must stay hard.

Today, under `plugins/saga/`, `/plan` §5.4 (`skills/plan/SKILL.md:730-787`) dispatches the plan reviewer, repairs the plan and dispatches again until no P0 or P1 remains, the operator overrides in one word, or the allowances (3 plus 2) run out (`:772-784`). The session writes `review_cycles` by hand. `/doc-review` describes the same loop (`skills/doc-review/SKILL.md:279-309`), reports P0 to P3 (`:222-234`), applies "safe" fixes in place (`:196-220`), and carries a cross-family reviewer seat plus a second-opinion step (`:146-195`). `/work`'s doc-review gate blocks on an open P0 or P1 unless the operator overrides in one word (`skills/work/SKILL.md:235-259`), and the override and safe fixes reach the issue comment through `scripts/issue_progress.py` (`:670-702`). The plan reviewer writes findings "in the shared finding schema the lens catalogue defines" (`plugins/agent-launcher/roles/plan-reviewer.md:120-121`).

The design (the program's `plan.md`, Change 8, "Plan review") replaces all of that with one reviewer, one pass, findings as C1 records, every finding answered, and a script-owned gate. C1 (issue #148) has landed, so `review_records.py` and its schema exist. X1a has landed in the lifecycle repository (revision `f8d0994`, "record saga's new review model and its contracts (#180)"), so the finding-format wording follows it. C15 (the Langfuse client) has not landed — no Langfuse client exists in fleet-core or saga — so the trace call stays out per the card's own rule.

## Requirements

Requirements are grouped by concern; R-IDs run continuously.

**Script and storage**

- R1. `python3 plugins/saga/scripts/plan_review.py record --issue <N> --plan <P> --findings <F>` validates the findings file as C1 finding records (subject `plan`, section locations) through C1's validator and stores one entry in the run record's `review_cycles`, with a fingerprint of the plan file. The script, not the session, writes the entry (AC-4).
- R2. `record` refuses a second review of the same plan revision: when the latest stored plan-review entry's fingerprint equals the current plan file's, it exits non-zero and writes nothing.
- R3. `plan_review.py answer` records exactly one answer per finding: `--fixed` names the plan section changed and is accepted only if the plan changed since the review; `--rejected` needs a `--reason`. A fixed answer on an unchanged plan, a rejection without a reason, an unknown finding id, a fixed answer naming no section, and a second answer to the same finding are each refused without writing (AC-2).
- R4. `plan_review.py check --issue <N>` exits non-zero while any finding is unanswered or the acceptance-criteria mapping fails, and 0 otherwise. It prints every rejection with its reason; rejections never hold the run. A mapping gap clears only by editing the plan until the mapping passes — it cannot be answered away (AC-1).
- R5. Storage reuses `review_cycles`; no new top-level run-record key. Every current reader of that array treats the new entries the way it treats C1's `review_run` entries: out of scope for its own count or decision.

**One pass**

- R6. `/plan` §5.4 dispatches the plan reviewer once, maps the acceptance criteria before dispatching, stores the findings through `record`, has the author answer every finding through `answer`, and gates on `check`. No repair loop, no cycle allowance, no operator override, no re-dispatch, and the reviewer never edits the plan (AC-3).
- R7. The §5.5 board-move trigger is the check exiting 0 with every finding answered. The `plan-review-floor` and `work-doc-review-floor` gate-record markers stay and describe the check.

**Finding records, no edits**

- R8. Standalone `/doc-review` on plans, requirements, strategy and issue documents reports C1 finding records instead of P0 to P3, never edits the document, and drops the cross-family reviewer seat and the second-opinion step. Its artifact stays under `docs/reviews/` (AC-3, AC-4).
- R9. A standalone review of a plan continues into `/work` only when the reviewed plan's check passes; any other document class still continues into nothing (AC-5).

**Gate and progress comment**

- R10. `/work`'s doc-review gate runs the check and blocks execution on a non-zero exit. There is no doc-review override; the evidence order names the check first (AC-5).
- R11. `issue_progress.py` carries the rejections in place of `--doc-review-fixes` and `--doc-review-override`. The `--review-gate-override` flag and its label stay exactly as they are (AC-5).

**Roles and pin**

- R12. `lifecycle-snapshot.json` is regenerated at the lifecycle revision where X1a landed, and the pin moves everywhere the roles suite names it — unless C8 or C11 already landed it, in which case this card only verifies and follows (AC-6).
- R13. The plan-reviewer, issue-reviewer and planner prompts name saga's finding record as the finding format. The plan reviewer fills the record's fields as C1 defines them — subject `plan`, a section location, the closest lens — and never writes a severity (AC-4).

**Suite**

## Key Technical Decisions

Each entry is the decision, then why, naming what was rejected.

- **KTD1. The plan-review entry lives in `review_cycles` with `loop: "plan_review"`.** C1 set the precedent: `run_record.TOP_LEVEL_KEYS` is frozen on purpose, so a review run reuses `review_cycles` rather than adding a thirteenth key. The entry carries `plan_path`, `plan_sha256` (the fingerprint at record time), `reviewed_revision` (the commit SHA, or `working tree`), the validated `findings`, and `answers` keyed by finding identity. Rejected: a new top-level key (same blast radius C1 refused: the Claude mod contract test and orchestrate fixtures mirror the key set), and reusing the hand-written cycle shape (the script owns this entry end to end, so it uses its own shape).
- **KTD2. "Changed since the review" is a SHA-256 of the plan file's bytes.** `record` stores the fingerprint; `answer --fixed` and the second-record refusal each recompute it and compare. A fingerprint survives worktrees, machines and vendors; a commit SHA does not exist for an uncommitted plan and moves for reasons unrelated to the plan. Rejected: reviewed-revision-against-current (answers the wrong question when the plan is uncommitted), and trusting the author's word that a section changed (the gate must stay hard).
- **KTD3. `check` imports the mapping and validation modules; it never shells out and never needs the network in tests.** It calls `functional_checks` mapping entry points and reads the issue body from `--body-file` in tests, from `gh` via `--issue` in real runs; `--record` takes an explicit record path the way `functional_checks.py write` does. Rejected: subprocess calls into sibling scripts (two CLIs to keep in sync, and failures arrive as text), and `gh`-only issue reads (untestable without network, which AC-6 forbids).
- **KTD4. Plan findings are validated but never graded.** They pass through C1's validator in input form — a handed-in severity is refused — and are stored without running the formula. The A–F grades are out of scope for this card, and no severity drives this gate. Rejected: computing severities "for the reader" (a stored severity nobody consumes is a second verdict that can disagree with the gate), and a plan-specific finding schema (every source emits the same records — the redesign's first rule).
- **KTD5. The re-pin is conditional and, when taken, atomic with its forced companions.** At implementation time the implementer first reads the pin: if C8 (issue #158) or C11 (issue #162) already moved it to X1a's revision, this card verifies the stamp and does nothing to the snapshot. Otherwise this card moves it, and the move lands in one commit with everything the roles suite forces: the snapshot, the pin in every prompt's source line and read-at-ladder, `index.json`, the suite's `SDLC_PIN`, a minimal `targeted-reviewer.md` wrapper plus its README map row, index entry, and aggregated-emits rule extension (C8's files; C8 extends the wrapper), and the `builder_record` field named in the three implementer prompts' output-contract sections (C11's files; C11 adds the declaration duty). The reasons are mechanical: `test_prompts_cover_every_staffable_lifecycle_role` demands exact prompt-to-role coverage and X1a adds the `targeted_reviewer` role; the new role sends no contract, so the aggregated-emits exemption extends to it; and `test_prompt_names_every_required_contract_field` demands every required field named and X1a adds `builder_record` to `implementation-result`. Rejected: re-pinning without the companions (AC-6 goes red), and blocking C12 on C8 or C11 (the card orders the race by landing, not by dependency).
- **KTD6. `issue_progress.py` replaces the two doc-review flags with `--doc-review-rejections`; the review-gate flag is untouched.** The removed flags are an internal CLI with two callers (`/work`'s Phase 4.3 and the tests), so they are removed, not deprecated — a deprecated override flag next to a gate with no override is a lie waiting for a caller. Each rejection renders as one list item carrying the finding and its reason. Rejected: keeping `--doc-review-override` for "emergencies" (the card deletes the override because nothing stays open after the pass), and folding rejections into `--doc-review-findings` (findings are what was found; rejections with reasons are what the operator must see).
- **KTD7. The Langfuse trace call stays out of this card.** C15 has not landed, and the card says to leave the call out in that case; whichever of C12 and C15 lands second adds it under C15's posting rules. AC-4's trace clause is conditional on C15 ("once C15 has landed"), so this card proves the storage and standalone-reporting clauses and records the trace as a later item. Rejected: posting behind a hand-rolled client (C15 owns the client, the trace shape and the posting rules), and a dead `--langfuse` flag waiting for C15 (a flag nobody can exercise is untested surface).

## High-Level Technical Design

One pass, three script steps, one gate. The session carries the reviewer's output to the script; the script owns everything after that.

```mermaid
flowchart LR
    R[plan reviewer: one pass, findings as C1 records] -->|findings file| REC[plan_review record: validate, fingerprint plan, append to review_cycles]
    REC --> ANS[author answers each: fixed names section, rejected needs reason]
    ANS --> CHK[plan_review check: unanswered or mapping gap exits non-zero, prints rejections]
    CHK -->|exit 0| W[/work gate passes]
    CHK -->|non-zero| B[/work blocks]
```

`record` refuses when the plan fingerprint matches the latest stored review (R2) and when any finding fails C1 validation. `answer` recomputes the fingerprint for a fixed answer (KTD2). `check` runs the unanswered scan first, then the mapping through `functional_checks` (KTD3); its text printout is what `/plan` §5.4 and `/work`'s gate show an attending operator, and `--json` serves the tests. The plan path stored in the entry resolves at check time as given, else against the primary work tree (the parent of `git rev-parse --git-common-dir`, per the run-record store-root rule — the command itself prints the `.git` directory, not the checkout), so `/work` can run the check from another worktree; a plan file found in neither place is a refusal naming the path.

### U1. `plan_review.py`: record, answer, check

The script that stores plan-review findings and owns the gate.

**Goal:** `record`, `answer` and `check` behave per R1–R4, store one entry per review in `review_cycles`, and leave every other reader of that array unaffected.

**Requirements:** R1, R2, R3, R4, R5.

**Dependencies:** none.

**Files:** `plugins/saga/scripts/plan_review.py` (create); `plugins/saga/references/run-record.md` (modify: the `plan_review` entry beside C1's "Review runs and builder records"); `plugins/saga/scripts/saga_spore.py` (modify: skip `plan_review` entries in the cycle count — outside the card's file list, named with the reason in the commit); `plugins/saga/tests/test_plan_review.py` (create); `plugins/saga/tests/fixtures/plan_review/` (create: `plan.md`, `body.md`, `findings.json` with two findings of valid C1 identity, `record.json`).

**Approach:** Standard library and PyYAML only. Three subcommands plus `--help` (picked up automatically by `test_entrypoints.py`, which globs every script carrying argparse):

- `record --issue <N> --plan <P> --findings <F>` (or `--record <path>` for an explicit record, mirroring `functional_checks.py write`). Validates `F` as a list of C1 findings through `review_records` — subject must be `plan`, every location a `section` scope, no severity — then appends `{loop: "plan_review", plan_path, plan_sha256, reviewed_revision, findings, answers: {}}` through `run_record.update` under the record lock. Refuses (exit 2, names the cause, writes nothing): a malformed finding, a finding whose recomputed identity mismatches, and a plan whose fingerprint equals the latest stored plan-review entry's (R2). Exit codes are the `functional_checks.py` table exactly: 0 ok, 1 the `check` gate below, 2 any refusal or anything that cannot run.
- `answer --issue <N> --finding <id> (--fixed <S> | --rejected <T>)` (or `--record`), where `<S>` is the plan section changed and `<T>` the rejection reason. Refuses with exit 2 an unknown id, a second answer to the same finding, `--fixed` with a blank section, `--fixed` when the recomputed fingerprint still equals the stored one, and `--rejected` with an empty reason. Answers land through `run_record.update`, carrying every other row and top-level key forward.
- `check --issue <N>` (or `--record` with `--body-file`). Prints each unanswered finding (identity, section, statement), then runs the mapping and prints each gap; exits 1 while either is non-empty. On exit 0 it prints every rejection as `rejected: <statement> — <reason>` (and a `no rejections` line when there are none, so an empty printout never reads as a skipped gate). `--json` prints the same as data for the tests.

The fixture findings carry valid identities computed once with the real `finding_identity` function; a tamper test then proves a mismatched identity is refused. The fixture plan proves the fixture body's single criterion, so the end-to-end check below exits 0 at the end.

**Patterns to follow:** `plugins/saga/scripts/review_records.py` (`record-run`/`record-builder` store handling, `run_record.update` writer shape); `plugins/saga/scripts/functional_checks.py` (`--issue`/`--record`/`--body-file` flags, exit-code table, text-plus-`--json` reports); C1's U3 "other readers ignore it" treatment for `review_cycles` consumers.

**Test scenarios:**

- Happy path: record two findings, answer one fixed after editing the plan and one rejected with a reason, check exits 0 and prints the rejection with its reason.
- Record: findings located by plan section pass C1's validator; a code finding, a finding with a severity, and a finding whose identity was tampered with are each refused by name; a second record on the unchanged plan is refused; after a plan edit a second record lands as a second entry.
- Answer: fixed with a blank section refused; fixed on the unchanged plan refused; fixed after the edit accepted; rejection without a reason refused; rejection with a reason accepted; unknown finding id refused; second answer to the same finding refused.
- Check: names each unanswered finding and exits 1; with every finding answered but a mapping gap, exits 1 naming the gap; a mapping gap has no answer path (answering the criterion id as a finding id is refused as unknown); all answered plus mapping passing exits 0 and prints every rejection.
- Storage: the entry round-trips through the record with every field; a concurrent usage write between load and save survives (the C1 U3 lock test shape); `release_step`, `cost_report`, `run_status` and `review_result` already skip non-`code_review` loops and schemas, and `saga_spore.py`'s counter is extended to skip `loop == "plan_review"` entries, so all five return the same results with and without the new entry present.
- Exit codes: every `record`/`answer` refusal above exits 2; `check` exits 1 on unanswered findings and on a mapping gap, 2 when the record or plan cannot be read.
- No network: every test in this file runs with `socket.socket` replaced by one that raises.

**Verification:** the end-to-end CLI scenario below passes; every refusal names its cause; the five `review_cycles` readers behave identically with the new entry present.
