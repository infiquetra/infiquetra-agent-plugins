# orchestrate: one targeted reviewer per review, two on high-risk cards (issue #159)

## Summary

In a run orchestrate drives, a review is one review controller plus one targeted reviewer. Orchestrate starts that reviewer through agent-launcher's existing reviewer launch, then hands the answer file and the session result back untouched. A record whose risk tier is high or very-high also starts one `external-reviewer`, on another staffed vendor when the run has one, on the same packet and without the first answer.

---

## Problem Frame

Issue #159 is card C9 of the saga review redesign (parent issue #147). C1 (issue #148) already wrote the review records and the merge answer. C8 (issue #158) already starts the targeted reviewer headless with `launcher.py review`. Nothing in orchestrate calls that launch. The controller is still described as running a lens consensus, and orchestrate still routes only `review_result.v2`.

Today, in this tree:

- One review phase admits one `review-controller`, plus named `external-reviewer` seats. `assert_review_transport` (`plugins/orchestrate/skills/orchestrate/scripts/orchestrate.py:1391`) refuses a plain review prompt and a second code-review unit. `plan-check` (`:2860`) runs that check and reads no run record.
- Every seat, including the external reviewer, is a Herdr pane. `go` (`:3612`) creates a worktree and calls `launch`.
- `launcher.py review` (`plugins/agent-launcher/skills/agent-launcher/scripts/launcher.py:3156`) is a different door. It needs a packet directory, writes `answer.json` and `result.json` under `--out` (`:2972`), and refuses before a session when the packet is missing. Roster already marks `targeted-reviewer` headless because the packet does not exist when panes are opened (`plugins/agent-launcher/skills/agent-launcher/scripts/roster.py:96`).
- `_review_routing_fields` (`orchestrate.py:1455`) accepts only `schema: review_result.v2` and the four outcome words. A repair needs `fix_requests` with `owner`, `fix_id`, and `touched_paths`. The note check (`:3777`) looks for those same four words.
- C1's review run (`plugins/saga/references/review-records.schema.json`, `review_run`) has `merge.allowed` and `merge.blocking`. It has no outcome word and no fix request. `plugins/saga/references/review-records.md` says nothing calls these records until the review command.
- `admission.risk_tier` is `low`, `medium`, `high`, or `very-high` (`plugins/saga/scripts/admission.py:121`, `plugins/saga/scripts/run_record.py:387`). The orchestrate test fixture leaves it null (`plugins/orchestrate/tests/fixtures/saga_run_record.py:295`).
- The agent-launcher floor in `plugins/orchestrate/com.infiquetra.claude/plugin.json` is `>=1.4.0`. `_declared_agent_launcher_floor` (`orchestrate.py:1969`) reads it. The companion in this tree is still version `1.7.2`, and `launcher.py review` is recorded under `[Unreleased]` in `plugins/agent-launcher/CHANGELOG.md`.

The card depends on C1 and C8. Both are already in this tree. The review command that writes the packet and calls `finish` is C10a, and it is out of scope here.

## Key Technical Decisions

- KTD1. **The reviewer starts when the controller calls `review-launch`, after the packet exists.** `go` keeps launching the controller as a pane. It does not launch a `targeted-reviewer` or, once the tier check is in place, an `external-reviewer`. Those two roles get no worktree and no pane, and they are removed from `go`'s launch slice before the concurrency cap is applied, so a pending reviewer cannot take a worker's slot. Rejected: admitting the reviewer as a pane through `expand` and `go`. That path calls `launcher.py launch`, starts before the packet exists, and is the door C8 and the sandbox follow-up (#189) already refused for this role.
- KTD2. **`review-launch` moves two files and does not read them.** The command is `orchestrate.py review-launch --issue N --seat targeted-reviewer|external-reviewer --packet DIR --repo DIR --head SHA [--out DIR] [--controller NAME]`. It resolves saga's prompt and schema through the same script discovery as `run_record.py`, by importing `reviewer_answer.paths`. It then runs `launcher.py review` with exactly `--vendor`, `--model`, `--effort`, `--repo`, `--head`, `--packet`, `--prompt`, `--schema`, and `--out`. It does not pass `--open-search-cap`, `--timeout`, or a settings path. The launcher's defaults stay. On exit 0 the answer and result bytes are whatever the launcher wrote. Orchestrate prints the two paths and the launcher's exit code. It does not parse either file, so an answer that is not JSON still returns the launcher's exit code, and a canary planted in the answer does not appear on stdout or in the unit note. A missing packet directory, a missing seat's staffing row, or the wrong tier for `external-reviewer` exits 2 before the subprocess. `--repo` must be the run repository. `--packet` must resolve inside the store root, the run repository, or a unit worktree. `--out` must resolve inside the store root and must not resolve to the other seat's out directory. Those four refusals also exit 2 before the subprocess.
- KTD3. **The out directory is per seat and outside every worktree.** The default `--out` is `<store root>/review-launch/issue-<N>/<seat>/`, and a lifecycle name is added when the controller has one. Two seats never share a directory, so the second launch cannot be pointed at the first answer by accident. The controller passes those paths to `finish`. Orchestrate does not call `finish`.
- KTD4. **The second vendor is chosen from staffing, in sorted role order.** The first reviewer is the `targeted-reviewer` row's vendor, model, and effort. The second is the first other row, roles sorted by name, whose vendor differs. If every other row uses the same vendor, or there is no other row, the second uses the first reviewer's vendor, model, and effort, which is the card's "exactly as the first" case. A staffed vendor with no reviewer recipe is surfaced as the launcher's refusal. Orchestrate does not fall back to the first vendor. `lens-reviewer` may still be a staffing row; using its vendor does not create a lens unit.
- KTD5. **The risk tier is applied in `start`, `expand`, and `go`, and nowhere in `plan-check`.** `high` and `very-high` require one `external-reviewer` for each review controller's lifecycle. `start` adds that unit when it is missing, before `git branch`, and refuses before the branch when staffing cannot name its vendor. Any other tier, including a null tier, refuses an `external-reviewer` that is already present, also before the branch. `expand` refuses an incoming seat that would break the count, and adds the missing high-tier seat only in `cmd_expand` after validation, so `launch-table --issue` does not mutate the run. `go` repeats the count check before `make_worktree`. A plan may contain zero or one `external-reviewer` per lifecycle at `plan-check` time. Two is a plan-shape refusal inside `assert_review_transport` and does not need the record. `plan-check` and `start` share that message.
- KTD6. **A lens roster is a `lens-reviewer` role, and the targeted reviewer is optional on old plans.** `assert_review_transport` refuses any unit whose role is `lens-reviewer`, and it refuses a second `targeted-reviewer` in one lifecycle. It does not require a `targeted-reviewer` unit. Existing controller-only plans keep loading. The new admission test is the positive case: one controller plus one `targeted-reviewer` passes `plan-check` and creates nothing. The second-controller message stays the one `assert_single_review_controller` already raises, so `plan-check` and `start` already share it. The lens-roster message is raised from the same function, which both commands call through `validate_plan`.
- KTD7. **A review run projects onto today's routing envelope. Orchestrate does not recompute the merge.** `schema: review_records.v1` and `kind: review_run` map `merge.allowed: true` to outcome `accepted`, and `merge.allowed: false` to `repairs_requested`. `merge.blocking` becomes one fix request per id. `fix_id` is the finding id. `owner` is `review-fixer`. `touched_paths` is `location.file`, or `location.document` when `location.scope` is `section`, and that path goes through `_route_path`. A path `_route_path` refuses is a routing refusal that names the finding id. The verbatim record stays stored. No other finding field is copied. A canary in `statement` must not appear in the worker prompt. `merge.report_only_blocks` is not routed. When `allowed` is true, blocking ids are not routed either. `review_result.v2` is unchanged, including its own `owner` values. `cycle_cap_best_available` and `review_incomplete` stay words of that old shape only. The note check keeps the same four words. A review run's `round`, when both the stored and the incoming artifact have one, is what the cycle-regression check compares. A shorter round is refused. Overwriting a terminal `accepted` or `cycle_cap_best_available` with a different artifact is still refused.
- KTD8. **The floor number moves to `>=1.7.2`, and `review-launch` also checks the subcommand.** This tree's `plugins/agent-launcher/plugin.json` says `1.7.2` and the source contains `launcher.py review`. The published `1.7.2` note is dated 2026-10-04 and does not mention that subcommand, so the number alone cannot prove the capability. `_validated_agent_launcher` keeps warning, rather than refusing, when the companion is below the numeric floor. `review-launch` refuses, with the existing update remedy, when `launcher.py review --help` exits non-zero. Ordinary `go` of a worker stays available against a launcher that can still open panes. Orchestrate's own package version stays `6.1.0`. Neither `plugins/orchestrate/plugin.json` version field nor `.claude-plugin/marketplace.json` changes. The surface test pins `6.1.0`, and no acceptance criterion asks for a new orchestrate version, so the bump waits for a release commit. The Unreleased changelog is the record. The command file's install sentence moves from agent-launcher 1.4.0 to 1.7.2.

## High-Level Technical Design

The controller session runs the review command. That command writes the packet. The controller then calls `review-launch` once per seat. Orchestrate calls `launcher.py review` and prints the two paths. The controller passes those paths to `finish`. This card does not implement `prepare` or `finish`.

| Step | Who | What moves |
| --- | --- | --- |
| Admit the plan | `plan-check`, `launch-table`, `start` | One controller. A `targeted-reviewer` unit is allowed. A `lens-reviewer` unit is refused. No run record is read |
| Apply the tier | `start`, `expand`, `go` | `high` or `very-high`: one `external-reviewer`. Anything else: none. Refusal happens before a branch or a worktree |
| Launch seats | `review-launch` | `launcher.py review` for each seat, distinct `--out`, same `--packet`. Answer and result stay unread |
| Route the record | `review-result` | A review run projects to an outcome word and fix requests. `review_result.v2` still routes as it does today |

`go` launches the controller and every ordinary unit. Reviewer roles are not in that slice.
