# Saga pane results as JSON strings, setup steps, and the empty-installable state (issue #218)

## Summary

Saga's three pane tools answer every `tool.call` with an object the session rejects, so no pane can report back; the setup pane also hides the survey's optional steps and dead-ends when nothing can be installed. This plan returns each tool's status as a JSON string the session accepts, lists the survey steps with a run path, and replaces the dead end with an explainer and Done.

---

## Problem Frame

This is a defect against the saga review redesign (parent issue #147), found during card K2's operator steps: on Claude Code 2.1.296, `/saga:setup` opened its pane and the `mcp__saga__setup` call failed at once with "tool.call step resolved mcp__saga__setup with a result that does not match its output shape … expected string, received object". Each `tool.call` hook in `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx:129-180` returns `{ result: { status, ... } }`, and the admission-review (`mods/admission-review.tsx:272-334`) and merge-confirmation (`mods/merge-confirmation.tsx:193-262`) hooks do the same on every return path. The session validates a hook's answer against the tool's output schema — a string, an array of content blocks, or nothing — so an object is refused and the operator's choice never reaches the agent. The merge-confirmation pane gates merges, so its failure blocks the review lifecycle.

CI runs `claude plugin validate --strict` and `claude plugin test` on 2.1.286 and 2.1.289 only (`.github/workflows/ci.yml:85`) and passes. Worse, the passing suite proves nothing about the shape: the mod suite passes 227 tests on 2.1.296 today with object results in place, because the test kit resolves `$.tool.call` without running the output-schema check. The fix must hold on the newest build as well as the pinned ones, and its tests must fail on objects, not just pass on strings.

The setup pane has two further faults. It draws only `survey.tools` and never `survey.steps`, so the `outcome-schedule` step from #214 cannot run from the pane even though the survey already reports each step's `{name, summary, done}` (`plugins/saga/scripts/saga_setup.py:797-801`, `:599-614`). And when no visible row has an install command, Install prints "Tick at least one tool with an install command." in red (`mods/setup-pane.tsx:221-224`) and leaves the operator nothing to do but Done or Dismiss.

## Requirements

Requirements are grouped by concern; R-IDs run continuously.

**Result shape**

- R1. Every return path of the three `tool.call` hooks yields `{ result: <string> }`, where the string is the compact JSON of the tool's documented status object — submitted, dismissed, not-placed, unavailable, nothing-to-review, timed-out or error — so the session accepts it on 2.1.296 and on every build in the CI matrix (AC-1, AC-2).
- R2. Each tool's tests cover every status in R1, asserting the result is a string that parses back to the documented object; this fills the two gaps in today's suite, setup's nothing-to-review and admission's timed-out (AC-1, AC-2).

**Setup steps**

- R3. The setup pane lists the survey's optional steps with their name, summary and done state, and runs a step the operator picks through `saga_setup.py step --name`, showing its progress and output (AC-3).

**Empty-installable state**

- R4. When no survey tool row has an install command, the setup pane shows no Install button, no red error, and an explainer that nothing here installs, offering only Done (AC-4).

**Skill, matrix and changelog**

- R5. The setup skill describes the pane's JSON-string result and still falls back to the script survey — print its table, ask which tools to install — when the pane returns anything but submitted (AC-5).
- R6. The CI matrix runs the mods job on 2.1.296 beside the 2.1.286 floor and 2.1.289; `validate --strict` and `plugin test` pass on each; the changelog's Unreleased Fixed section names issue #218 with no version bump (AC-1).
- R7. When `survey.tools` is empty but `survey.steps` is not, the setup pane still opens and lists the steps instead of returning nothing-to-review, so `outcome-schedule` stays reachable (AC-3).
- R8. `docs/engineering-journal/LEARNINGS.md` records that Claude Code 2.1.296 refuses object tool results and that `claude plugin test` runs no output-schema check, with the probes as evidence (repo rule: the AGENTS.md journal standard; no AC).

## Key Technical Decisions

Each entry is the decision, then why, naming what was rejected.

- **KTD1. Every return path yields `{ result: JSON.stringify(statusObject) }`, compact, through one shared helper.** Two live probes on 2.1.296 settle the shape: an object result is refused with `invalid_union`, expected string, array or undefined and received object, while the same object as a JSON string reaches the model, which reads the status back out. The build's own declarations agree: `ToolCallResult` says core validates a hook's answer against the tool's output schema when it has one, and the runtime runs `outputSchema?.safeParse` on the hook's answer before mapping it for the model. Compact JSON keeps transcripts small and parses back with one call. Rejected: content-block arrays (nothing needs blocks, and every caller would still parse the text block); per-mod inline `JSON.stringify` (three copies that drift on the next status added); declaring an object output schema on the tool (`ToolSpec` carries only name, description, inputSchema and isDeferred — there is no output-schema field to declare).
- **KTD2. The helper lives in a new `mods/pane-result.ts`, outside the card's file list.** `paneResult(outcome: unknown): string` is the one writer; the tests parse back with `JSON.parse` after asserting `typeof result === 'string'`, so an object regression fails instead of passing. A new module keeps the concern in one place across all three tools. Rejected: `run-record.ts` (its readers parse script output; stringifying tool results is a different concern in the opposite direction), and asserting parse-back alone (a test that coerces before parsing would pass on objects, repeating the kit's blind spot).
- **KTD3. A picked step runs as `saga_setup.py step --name <name>` with no `--repo`, the process cwd set to the saga checkout the skill uses.** The tool call walks up from `$.plugin.root` — itself, then three parents — and takes the first directory holding `plugins/saga/scripts/saga_setup.py`, probed through `$.fs.exists`; that checkout becomes the step run's cwd, so the step vectors resolve exactly as the skill's from-the-checkout form. The pane's repo and any model-supplied path never steer a step: a checkout under setup that contains the relative vector would otherwise execute its own file. When no checkout is found the steps render unrunnable with the reason shown, and a failed `fs.exists` reads as absent, so suites that never stub it stay green. `setupStepArgv` and the step types land in `run-record.ts` and `types/index.d.ts`, both in the card's amended file list. Rejected: `--repo <repo>` (runs the vector in the checkout under setup, where it misses the plugin script and can hit an attacker's file); suffix-stripping the plugin root (assumes one install layout and is untestable in the kit, whose root is a sandbox dir); platform-gating `outcome-schedule` in the pane (the card doesn't ask; a later item).
- **KTD4. The empty-installable state offers only Done.** When no tool row has `has_install`, the pane hides Install and Dismiss, explains that nothing here installs, and Done returns submitted with empty installed and failed lists — the honest "settled, nothing to do" signal, after which the skill runs the survey and continues with its questions. Rejected: keeping Dismiss (it sends the skill back to "which tools to install" for rows that can never install — the same dead end one step later); auto-returning without showing the pane (the operator must see the explainer); touching the distinct unticked-everything error (an operator choice with installable rows present, which stays red and stays tested).
- **KTD5. The matrix adds exactly 2.1.296, the build that rejects objects; the floor stays 2.1.286.** 2.1.296 is verified installable from npm and is the build the probes ran on. The floor test pins only that the matrix exercises `CLAUDE_CODE_FLOOR_VERSION`, so the addition keeps it green. Rejected: replacing 2.1.289 with 2.1.296 (the middle build guards the range the mods were written against); expecting the matrix to catch a shape regression (the kit runs no schema check — R2's typeof assertions are the guard, the matrix guards API drift).

## Implementation Units

Four units: the string results with their status tests, the setup steps, the empty-installable state, then the skill, matrix and changelog.

### U1. String results in every return path

Every `tool.call` answer becomes a JSON string, and every status of every tool is tested as one.

**Goal:** The three pane tools return `{ result: <compact JSON string> }` on every path, and each tool's suite proves every status is a string that parses back to the documented object.

**Requirements:** R1, R2.

**Dependencies:** none.

**Files:** `plugins/saga/com.infiquetra.claude/mods/pane-result.ts` (create: `paneResult` — in the card's amended file list); `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx` (modify: the seven return paths at `:129-180`); `plugins/saga/com.infiquetra.claude/mods/admission-review.tsx` (modify: the eleven return paths at `:272-334`); `plugins/saga/com.infiquetra.claude/mods/merge-confirmation.tsx` (modify: the ten return paths at `:196-255`; the timeout-submit error leaves through `:253` as the outcome `submitTimeout` returned); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx` (modify: parse-back assertions, the new nothing-to-review test); `plugins/saga/com.infiquetra.claude/mods/admission-review.test.ts` (modify: parse-back assertions, the new timed-out test); `plugins/saga/com.infiquetra.claude/mods/merge-confirmation.test.tsx` (modify: parse-back assertions).

**Approach:** Add `paneResult(outcome: unknown): string` returning `JSON.stringify(outcome)` with no pretty-print, and wrap every `tool.call` return in the three mods — submitted, dismissed, not-placed, unavailable, nothing-to-review, timed-out and each error shape — keeping every status object byte-identical and changing only the envelope from object to string. The outcome types in `types/index.d.ts` (`SagaSetupOutcome` and its admission and merge siblings) stay as the documented JSON payloads; nothing there changes. The merge timeout path keeps its rule: a timeout the script refuses returns an error naming the failure, never a timed-out the script never saw. In the tests, every assertion on a tool result first asserts `typeof result === 'string'` and then compares `JSON.parse(result)` to today's expected object — the typeof line is what fails on an object regression, since the kit itself won't. Add the two missing status tests in the established world-stub style: setup with a survey whose tools list is empty returns nothing-to-review and opens no pane; admission with one-millisecond sleeps runs the full 1,800-second wait and returns timed-out with no answers call.

**Patterns to follow:** `plugins/saga/com.infiquetra.claude/mods/run-record.ts:82-86` (`sagaScriptArgv`, the shared-helper precedent the three mods import); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx:235-242` (the thirty-minute timed-out test admission's copies); `plugins/saga/com.infiquetra.claude/mods/merge-confirmation.test.tsx:320-327` (the refused-timeout error test).

**Test scenarios:**

- Happy path: each tool's submitted path yields a string parsing back to the documented submitted object with its ids, answers or summary.
- Dismissed: the Dismiss press and the window-close path each yield a string parsing back to `{status: 'dismissed'}` with no script recording call (admission and merge cover both; setup covers the button).
- Not-placed and unavailable: an unplaceable pane and a mobile-only surface each yield strings parsing back to the documented reasoned objects, with no wait slept.
- Nothing-to-review: setup with an empty tools list and no steps, admission with neither question outstanding, and merge with no pending choice each yield a string parsing back to `{status: 'nothing-to-review'}` and open no pane. (Setup with steps but no tools opens the pane instead — R7, tested in U2.)
- Timed-out: the full 1,800-sleep wait yields a string parsing back to `{status: 'timed-out'}`; merge additionally submits exactly `{"answers": {}, "pane_timeout": true}` to the repository-qualified answers argv, and a refused timeout submit yields an error string naming the failure.
- Error: a failing survey, an unknown survey version, a failing admission dry run, an unknown review version, a failing review read, a bad issue input, a second open pane, and a merge repo mismatch each yield strings parsing back to error objects naming the cause.
- Regression guard: a test asserting `typeof result === 'string'` fails if any path returns the bare object; the suite passes on 2.1.296.

**Verification:** the mod suite below passes with the converted assertions and the two new tests in it; the no-object-results pin below finds no `result:` line without `paneResult(` in the three mods; the plan and work skills' "read the status it returns" prose still describes the returned JSON (read-only check — any reword is a later card, not this unit). AC-2 is a real session no CI command can run, so the builder proves it live: start Claude Code 2.1.296 with `--plugin-dir` on this checkout's saga plugin in a new Herdr tab, run `/saga:setup`, press Dismiss and read that the agent received `dismissed`, then run an install that submits and read the installed and failed ids; the outcome is recorded per-criterion in `.program/acceptance.md`.

### U2. The survey steps in the setup pane

The pane lists the optional steps with their done state and runs the one the operator picks.

**Goal:** Steps from the survey render with name, summary and done state, and a Run press executes the step through `saga_setup.py step --name` with progress shown.

**Requirements:** R3, R7.

**Dependencies:** U1 (the step runner's outcomes return through `paneResult`).

**Files:** `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx` (modify: the steps section, the checkout probe, the step runner, the R7 early-return change); `plugins/saga/com.infiquetra.claude/mods/run-record.ts` (modify: `setupStepArgv` beside `setupInstallArgv` at `:442`, and the checkout walk — in the card's amended file list); `plugins/saga/com.infiquetra.claude/types/index.d.ts` (modify: the `SagaSetupStep` shape, the survey's optional `steps` field and the review's `stepProgress` and `checkout` fields beside `SagaSetupSurvey` at `:494-498` — in the card's amended file list); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx` (modify: the steps tests); `plugins/saga/com.infiquetra.claude/mods/run-record.test.ts` (modify: the `setupStepArgv` case beside `setupInstallArgv` at `:406-424` — in the card's amended file list).

**Approach:** Read the steps defensively — a missing or non-array `survey.steps` draws no Steps section — and draw each step's name, its summary, and done or not done under the tool rows. The early return at `setup-pane.tsx:147-148` fires only when the tools list is empty and no steps are present (R7). After the survey read, the tool call probes the saga checkout by walking up from `$.plugin.root` for `plugins/saga/scripts/saga_setup.py` through `$.fs.exists` (KTD3) and stores it in pane state; steps render Run buttons only when a checkout was found, else the unrunnable reason. A Run press calls `setupStepArgv($.plugin.root, name)` — `saga_setup.py step --name <name>` with no `--repo` — with the process cwd set to the stored checkout, one step at a time, moving the step through running, done or failed with the script's output shown. Step run state lives on its own `stepProgress` field, never in Install's `progress` map, so a step can never be submitted as a tool id and Done's loop is untouched. The pane timeout on the run sits above the script's own 30-second child timeout so the engine never wins the race. A failed step shows the script's stderr and leaves the pane open; a step run never changes what Done submits. Steps render and run independently of the tool rows, so a survey with steps but no installable row still offers its steps above the U3 explainer.

**Patterns to follow:** `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx:214-247` (Install's guarded run with epoch, per-row progress and first-failure stop); `plugins/saga/com.infiquetra.claude/mods/run-record.ts:442-445` (`setupInstallArgv`, the argv shape `setupStepArgv` mirrors); `plugins/saga/scripts/saga_setup.py:1115-1140` (`run_named_step`, the verb the argv reaches).

**Test scenarios:**

- Happy path: a survey with two steps draws each name with its summary and done state; pressing a step's Run calls `saga_setup.py step --name <name>` once with the process cwd set to the probed checkout — the stub records `init.cwd` and asserts it equals the checkout the `fs.exists` stub admitted — and shows the step's output with a done mark.
- Steps without tools: a survey with an empty tools list and one step opens the pane and lists the step with a working Run instead of returning nothing-to-review (R7).
- Unrunnable: when no probed directory holds the plugin script, steps render with the unrunnable reason and no Run buttons, and nothing runs.
- Done state: a step the survey marks done still offers Run; running it re-executes the verb.
- Failure: a step whose verb exits non-zero shows the stderr, marks the step failed, and leaves the pane open with Done still submitting only the install lists — the step never appears in installed or failed.
- No steps: a survey with an empty steps list, and one with the field missing or not an array, draws no Steps section and changes nothing else; the existing fixture carries `steps: []`.
- Checkout walk: the walk takes the first directory holding the plugin script, the plugin root itself included, and returns null past three parents or when every probe fails or rejects.
- argv pin: `setupStepArgv` builds exactly `['python3', '<root>/scripts/saga_setup.py', 'step', '--name', name]` with no `--repo`.
- Outcome envelope: Done after a step run still returns a JSON string through `paneResult`.

**Verification:** the mod suite below passes with the steps tests in it; the survey command below shows the steps document the pane reads.
