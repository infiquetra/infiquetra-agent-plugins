# The targeted reviewer's sandbox reads only what the review needs (issue #189)

## Summary

Reverse the read rule in the targeted reviewer's command sandbox: block the whole home directory and allow back only the scratch copy, the review packet and the toolchain paths the launch names. Hand sandboxed commands only environment variables on a named allow-list. Saga then scrubs known secret formats out of every reproduction's proof before it writes the finding record or builds the state it sends to Jev (TypeSafe's classifier).

---

## Problem Frame

This is a follow-up to card C8 of the saga review redesign (parent issue #147). C8 is issue #158, and PR #187 merged it. PR #187 gave agent-launcher a headless launch for saga's targeted reviewer. The reviewer runs tests from the change it reviews, inside Claude Code's command sandbox. `reviewer_claude_settings` (`plugins/agent-launcher/skills/agent-launcher/scripts/launcher.py:2182`) builds the sandbox from a per-launch `--settings` file. Nothing calls the launch yet; the single review command (card C10a) wires it in later. The card names three gaps, and this plan's measurements confirm the first two on the operator's Mac.

1. **Reads are blocked by a fixed list.** `denyRead` is the eleven entries of `REVIEWER_CREDENTIAL_PATHS` (`launcher.py:2088`). Anything else under the home directory stays readable to a hostile test. Measured on 2026-10-06 with the merged settings: canary files planted in the home directory, `~/.config`, `~/.local/share`, `~/.cache` and `~/.local/bin` were all readable from a sandboxed command.
2. **The environment is filtered by name.** `REVIEWER_CREDENTIAL_NAME` (`launcher.py:2084`) hides only variables whose names look like credentials. Measured: a canary variable with an ordinary name reached sandboxed commands until it was denied by name.
3. **Proof output is recorded and sent unscrubbed.** A test that reads a secret can print it. `reviewer_answer.py` copies the proof into the finding record as it is (`plugins/saga/scripts/reviewer_answer.py:477`, `to_records`). It also puts up to 4,000 characters of the output into Jev's state (`:432`, `jev_pick`). Fleet-core's TypeSafe client redacts state before sending it (`plugins/fleet-core/scripts/fleet_commons/typesafe_client.py:273`), but that does not protect the record. The redaction marker also does not say what was removed.

### What the installed Claude Code supports (measured before planning)

The card's stop condition is that Claude Code's sandbox may not be able to express "block home, allow these". So this plan measured it first, on Claude Code 2.1.292, through the real `claude -p` reviewer recipe with `haiku`, using only canary files and canary variables created for the run and deleted after it.

| Question | Result |
| --- | --- |
| `denyRead: ["~"]` blocks the home directory | Yes: every home canary read failed, and `ls ~` failed |
| `allowRead` re-opens a path inside a blocked `~` | Yes: the scratch copy and the packet (both under `~/.cache`) stayed readable |
| A canary beside the scratch copy, in the same reviews directory | Blocked: only the copy itself was allowed back |
| A Python test runs in the copy with home blocked | Yes: `python3 -m unittest` and `python3 -m pytest` both exited 0 (the interpreter sits outside home) |
| A binary under a blocked home runs | Yes, it runs, but its files cannot be read; so an interpreter under home would fail to load its standard library |
| `git --version` with home blocked | Fails with exit 128, because git cannot read its global configuration; with `GIT_CONFIG_GLOBAL=/dev/null` in the session's environment it exits 0 |
| `git init` in the copy | Fails with exit 128 under the merged settings too, so this plan does not cause it |
| `credentials.envVars` denying every name off an allow-list | Works with 155 names denied; tests and git still ran |
| Variables left in a sandboxed command | The allow-list, plus proxy and runtime variables the sandbox itself sets (its network proxy settings, `SANDBOX_RUNTIME`, its own temp-directory variables) |
| Claude's shell snapshot | Exports only `PATH`, so every other variable comes from the launch environment, which the allow-list governs |

Block-home-and-allow-back is supported, so the plan proceeds.

## Requirements

Requirements are grouped by concern; R-IDs run continuously.

**Reads**

- R1. The reviewer's sandbox settings block reads of the whole home directory (`denyRead` holds `~`).
- R2. `allowRead` holds exactly three kinds of path: the scratch copy, the review packet, and each toolchain path the launch names. Each entry carries its reason in the launch result.
- R3. A toolchain path is allowed back only when the interpreter on the session's `PATH` resolves under home, and only when the path, both as written and resolved, is not the home directory or above it, is not a shared root such as `~/.config`, and is not equal to, inside, or above any known credential path.
- R4. The launch refuses a scratch copy or packet path that fails the same test as R3.

**Environment**

- R5. Sandboxed commands receive only the variables on a named allow-list. Every other name in the launch environment is denied, whatever it is called.
- R6. The session's environment sets `GIT_CONFIG_GLOBAL=/dev/null`, so git runs with the home directory blocked.

**The probe**

- R7. `launcher.py reviewer-probe` plants a canary file in the home directory, outside the old list, and fails if a sandboxed command can read it. It also fails if the packet cannot be read, if a real Python test in the copy does not pass, if an ordinary-named canary variable reaches the command, or if git cannot run. It removes the home canary however it exits.

**Scrubbing**

- R8. Saga replaces known secret formats with a marker naming their kind, in every string of a finding's proof. The formats are GitHub tokens, AWS access key IDs, private-key blocks, the other formats fleet-core redacts, the credential formats `scripts/check_repo.py` bans (Stripe, Google and Anthropic keys among them), and long high-entropy strings. The finding's `statement` is scrubbed the same way. The marker looks like `[scrubbed:github-token]`. It is replaced before the finding record is built and before Jev's state is built.
- R9. Scrubbing runs before the 4,000-character cut, never after it. Running it twice changes nothing, and it leaves ordinary test output, file paths and content hashes alone.

**Records**

- R10. The engineering journal records the decision and what was measured, and both plugins' changelogs describe the change.

## Key Technical Decisions

- KTD1. Block `~` and allow back, not a longer list: the card's own argument, confirmed by measurement. The files that matter on a real machine have arbitrary names, such as a vault password file or an `.env` of provider keys, so no list stays complete. The rejected alternative, adding the card's seven missing paths to `denyRead`, is exactly what the card's stop condition forbids.
- KTD2. `denyRead` is `["~"]` plus the probe's `extra_deny_read`. `REVIEWER_CREDENTIAL_PATHS` leaves the sandbox: everything on it is under `~`. The list stays for two other jobs: the permission layer's `Read(...)` deny rules, which are unchanged in kind, and the containment check in KTD4. It gains the card's missing entries, because the containment check is only as good as the list: `~/.git-credentials`, `~/.pypirc`, `~/.cargo/credentials`, `~/.cargo/credentials.toml`, `~/.terraform.d`, `~/.vault-token`, `~/.config/hub`, `~/.local/share/keyrings` and `~/.npmrc`.
- KTD3. Toolchain paths are derived at launch from the session's `PATH`, not hard-coded: a fixed list names one machine's layout. The derivation covers uv-managed Python, pyenv, conda and a node install under home. For each command in `REVIEWER_TOOLCHAIN_COMMANDS`, which is `python3` and `node`, `shutil.which(cmd, path=env["PATH"])` finds the binary. Two candidate prefixes come from it: the unresolved one (`<which>/../..`, a virtual environment's directory) and the resolved one (`realpath(<which>)/../..`, the real install). A candidate outside home needs no allow-back and is dropped. Each allowed path is named with its reason, for example "python3 on the session PATH resolves here; its standard library and site-packages". Rejected: running the interpreter to ask for `sys.prefix`. That needs a subprocess and gives the same answer for the layouts that matter.
- KTD4. An allowed path must not re-open what home blocking closed. The test runs twice, on the path as written (made absolute against `env["HOME"]`, with `..` segments collapsed) and on its resolved form (symlinks followed), and the path fails when either form fails. A toolchain candidate is dropped, and recorded with its reason, when any of these is true: it is the home directory or an ancestor of it; it is one of `REVIEWER_SHARED_ROOTS` (`~/.config`, `~/.local`, `~/.local/share`, `~/.cache`, `~/Library`); or it is equal to, inside, or an ancestor of any `REVIEWER_CREDENTIAL_PATHS` entry. Being inside home is not itself a failure: the scratch copy lives under `~/.cache`. For example, `~/.local/bin/node`'s unresolved prefix `~/.local` is dropped and its resolved prefix is kept. The same test refuses the launch (`ReviewerRefused`, exit 2) when the scratch copy or the packet fails it, because those two are required.
- KTD5. The environment allow-list is a named tuple with a reason for each entry, not a name filter. `REVIEWER_ENVIRONMENT_ALLOWED` holds `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `LANG`, `TZ`, `TMPDIR` and `GIT_CONFIG_GLOBAL`, plus the two locale names `LC_ALL` and `LC_CTYPE`. No prefix is allowed: a rule like `LC_*` would let `LC_PLAIN` or `LC_TOKEN` through. That is what the measured Python test and git run needed. `reviewer_denied_variables(env)` returns every launch-environment name off the list, and `credentials.envVars` denies each one. `REVIEWER_CREDENTIAL_NAME` survives as a guard: a name that matches it is denied even if someone later adds it to the allow-list. Variables the sandbox itself injects are outside the launch environment and outside this control; they are recorded in the journal.
- KTD6. `GIT_CONFIG_GLOBAL=/dev/null` goes into the session's environment in `reviewer_session_environment`, overriding any inherited value: measured as what makes git run with home blocked. The Claude process sees it too. That is acceptable, because the copy has no `.git` and git configuration is not part of Claude's configuration. Rejected: allowing back `~/.gitconfig`, which can carry tokens in `url.<base>.insteadOf` rewrites.
- KTD7. The scrubber is saga's own kinded pattern table in `reviewer_answer.py`, not a call into fleet-core. Fleet-core's `redact_text` writes one anonymous placeholder, and the card wants the kind named. Fleet-core also loads only when Jev is asked, and the `--no-jev` path must still scrub the record. The table keeps parity with fleet-core's: a test checks that every format fleet-core redacts is also scrubbed. The high-entropy rule copies fleet-core's thresholds: a run of 40 or more characters from `[A-Za-z0-9+=_-]`, Shannon entropy of at least 4.0 bits, and hex content hashes exempt.
- KTD8. The marker in the text is the record's statement that something was replaced; no schema field is added. `review_records.v1` and the answer schema stay unchanged, which the card's non-goals require. A reader sees `[scrubbed:aws-access-key-id]` exactly where the value was.
- KTD9. Scrub every string in the proof (`test`, `command`, `output`, each entry of `steps`) and the finding's `statement`, not only `output`: the reviewer writes those itself and could quote what a test printed or a file it read. Scrubbing `statement` keeps it on one line, so the record validator's one-sentence rule still holds. `trigger` is not scrubbed: `check` refuses any value off `formula.TRIGGERS`, a closed list, so it cannot carry a secret.

## High-Level Technical Design

The reviewer's settings before and after, for one launch:

| Setting | Merged in #187 | After this plan |
| --- | --- | --- |
| `sandbox.filesystem.denyRead` | eleven credential paths | `~` (plus the probe's own extra path) |
| `sandbox.filesystem.allowRead` | absent | the scratch copy, the packet, each derived toolchain path |
| `sandbox.filesystem.denyWrite` | the temp roots | unchanged |
| `sandbox.credentials.envVars` | deny names matching the credential pattern | deny every launch-environment name off the allow-list |
| `permissions.allow` | `Bash`, `Edit(./**)`, the packet's `Read` | unchanged |
| `permissions.deny` | `WebFetch`, `WebSearch`, `mcp__*`, `Read(<credential path>)` | unchanged in kind; the credential list grows (KTD2) |
| Session environment | the launch environment minus API-key variables | the same, plus `GIT_CONFIG_GLOBAL=/dev/null` |

Saga's side, per finding in `to_records`: check the answer, then scrub the proof (R8, R9). The record gets the scrubbed proof. `jev_pick` receives the finding with the scrubbed proof, and scrubs `output` once more, before the 4,000-character cut, when it builds the state.

### U4. Saga: scrub secrets from proof before the record and before Jev

No known secret format in a reproduction's proof reaches the finding record or the state sent to Jev.

**Goal:** `reviewer_answer.py` gains `scrub_text` and `scrub_proof`; `to_records` and `jev_pick` use them.

**Requirements:** R8, R9; KTD7, KTD8, KTD9.

**Dependencies:** none (independent of U1 to U3).

**Files:**
- `plugins/saga/scripts/reviewer_answer.py`
- `plugins/saga/tests/test_reviewer_answer.py`

**Approach:**
- `SCRUB_PATTERNS: tuple[tuple[str, re.Pattern[str]], ...]`, applied in order, specific kinds before the generic ones:
  - `private-key`: a `-----BEGIN ... PRIVATE KEY-----` block through its `END` line. An unterminated `BEGIN` runs to the end of the text, because the reviewer's output may be cut.
  - `github-token`: `gh[pousr]_` followed by 20 or more letters and digits, and `github_pat_` followed by 22 or more word characters.
  - `aws-access-key-id`: `(A3T[A-Z0-9]|AKIA|ASIA|ABIA|ACCA)[A-Z0-9]{16}`.
  - `slack-token`: `xox[abposr]-…`.
  - `stripe-key`: `sk_live_` or `sk_test_` followed by 16 or more characters.
  - `google-api-key`: `AIza` followed by 35 characters.
  - `anthropic-api-key`: `sk-ant-` followed by 24 or more characters; it runs before the generic `sk-` kind.
  - `api-key`: `sk-` followed by 20 or more characters.
  - `jwt`: three base64url segments starting `eyJ`.
  - `bearer-token`: `Bearer` followed by a token.
  - `url-credentials`: `scheme://user:pass@`.
  - `named-secret`: an assignment to a secret-named key, with fleet-core's bounded expression.
  - `high-entropy`: KTD7's rule, with hex content hashes exempt.
- `scrub_text(text) -> tuple[str, list[str]]` returns the scrubbed text and the kinds replaced, using the marker `[scrubbed:<kind>]`. `scrub_proof(proof) -> tuple[dict, list[str]]` applies it to `test`, `command`, `output` and each `steps` entry, on a deep copy.
- `to_records` scrubs each finding's proof and `statement` after `check` passes. The record gets the scrubbed values, and `jev_pick` receives a copy of the finding carrying them. `jev_pick` also scrubs `statement` itself when it builds the state.
- `jev_pick` builds `"output": scrub_text(str(proof.get("output") or ""))[0][:4000]`: scrubbed first, then cut, so it is safe for any caller.
- Update the module docstring's `records` bullet to say proof is scrubbed first.

## Scope Boundaries

**In scope:** the Claude reviewer recipe's sandbox reads and environment, the probe, and saga's proof scrubbing.

**Non-goals (from the card):**
- Other vendors' reviewer launches. Only Claude has a recipe; every other vendor is refused by name.
- The review-tools runner's untrusted-head fixes (the separate follow-up to #151).
- The reviewer's prompt, answer schema and Jev verb.

**Deferred to follow-up work (later items, not units):**
- **Claude's Read tool follows the operator's own permission rules.** Measured during planning: under the reviewer's settings, Claude's Read tool (not a sandboxed command) read a home canary. Measured again on 2026-10-07 with user settings left out (`--setting-sources project`, for the measurement only): the same read was denied. So a user-level setting grants it, and permission allow lists merge across settings levels. `reviewer_claude_widening` checks the sandbox keys but not `permissions.allow`. Prompt-injected text in a reviewed change could therefore lead the model to read a credential file and quote it. This plan's scrubber masks known formats and long random strings in proof and `statement`, which narrows but does not close the gap. This needs its own card. The fix choices all reach past this card's sandboxed commands: refusing broad `Read` allow rules in `reviewer_claude_widening` would refuse every launch on the operator's machine until the operator changes their own settings; denying `Read` for every sibling along the path from home to the copy is new permission-layer machinery; and moving the scratch copy out of home changes the work-root layout. Recommended priority: high.
- Scrubbing the raw `answer.json` the launch writes to `--out`. That file stays on the operator's machine and is never sent.
- `git init` and other writes under `.git` fail in the copy. This is the case under the merged settings too; the cause is not measured.
- `uv run` inside the sandbox needs a writable cache; reads alone do not make it work.

## Risks & Dependencies

- **A Claude Code update changes how `allowRead` behaves inside a denied parent.** Mitigation: `reviewer-probe` checks the home canary and the packet read live, and C3's setup step calls the probe.
- **An operator whose `python3` lives under home in a layout KTD3 does not foresee.** The Python test would then fail to load its standard library. Mitigation: the probe's `python-test` verdict fails loudly, and `sandbox_reads.dropped` says which candidate was dropped and why.
- **Allow-listing too few variables breaks a test that needs one.** Mitigation: the measured Python test and git run pass with exactly this list, and the list is a single named constant to extend with a reason.
- **The scrubber misses a format.** Mitigation: the high-entropy rule catches long random strings, fleet-core still redacts the Jev state on transport, and the sandbox has no network.
