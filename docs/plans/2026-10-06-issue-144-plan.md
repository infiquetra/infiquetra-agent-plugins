# Stale review re-enters through the combined-branch gate (issue #144)

## Summary

Reword `/work` §5.3 so a stale review sends the branch back through the Phase 3.3 combined-branch loop and takes the new `REVIEWED_SHA` from `build_loop.py --handoff`, closing the one review-entry path that skips the gate issue #100 added. A prose-contract regression test pins the new wording.

## Problem Frame

Issue #100 made a passing combined-branch functional run the gate for code review, and `/work` §3.3, §5.1 and the coordinator ruling all say every entry into review comes through it.

But §5.3 handles a stale review by telling the worker to re-run `/code-review` while "capturing a fresh `REVIEWED_SHA`" directly. A worker following that sentence reviews either a revision no combined pass has checked or the old handed revision, so the #100 gate is skipped on the stale path.

A single-reviewer experiment on the issue #99 reviewed commit reported this as a major conformance finding on 2026-10-04. Neither of that issue's two review rounds caught it, and it is still present on main.

## Requirements

Five requirements, all taken directly from the card.

- R1. The "capturing a fresh `REVIEWED_SHA`" sentence is gone from the work skill: `grep -n "capturing a fresh" plugins/saga/skills/work/SKILL.md` finds nothing.
- R2. §5.3 sends a stale branch back through Phase 3.3 and takes the new `REVIEWED_SHA` from `build_loop.py --handoff`, exactly as §5.1 does, before re-running `/code-review`.
- R3. A regression test in `plugins/saga/tests/` asserts the §5.3 stale-review instructions name the combined-branch loop and `--handoff`, and fails on the current text.
- R4. `plugins/saga/CHANGELOG.md` records the fix under Unreleased.
- R5. The full saga suite stays green: `python3 -m pytest plugins/saga/tests -q --import-mode=importlib` passes.

## Key Technical Decisions

Four load-bearing choices that constrain the implementation.

- Reword §5.3 only and change no script: the gate, the combined-branch run and `--handoff` already exist from issues #99 and #100, so the defect is prose contradicting them; touching `build_loop.py` or `review_result.py` would widen the blast radius for no behavioral gain.
- Assert on the stale-review paragraph, not just the §5.3 section: "Phase 3.3" already appears in the repairs and cap bullets, so a section-wide presence check would pass on the broken text; the new test and the U1 check must target the slice from the stale paragraph opening through `### 5.4`, which excludes the outcome bullets.
- Pair every presence assertion with the AC-1 absence assertion: a fix that appends the routing sentence without deleting the old one would pass presence checks while leaving the contradiction; the old sentence must be gone.
- Put the contract in one new focused file, `plugins/saga/tests/test_work_stale_review_gate.py`, mirroring `test_work_prose_contracts.py`: one discoverable home for this gate's wording, using the established ROOT-walk and section-slice pattern rather than inventing a new harness.

## Implementation Units

Two units: the wording fix, then the regression test and changelog entry.

### U1. Reword the §5.3 stale-review path

Replace the capture-fresh sentence with a route back through Phase 3.3 and `--handoff`.

**Goal:** The §5.3 stale-review paragraph routes a moved branch through the Phase 3.3 combined-branch loop and the §5.1 handoff before re-review.

**Requirements:** R1, R2.

**Dependencies:** none.

**Files:** `plugins/saga/skills/work/SKILL.md` (modify).

**Approach:** Replace the sentence at `SKILL.md:952-953` ("A count `> 0` means commits landed since the review: keep PR-ready blocked and re-run `/code-review`, capturing a fresh `REVIEWED_SHA`, before any PR/merge offer") with wording that keeps PR-ready blocked, runs the Phase 3.3 combined-branch loop on the new head until green, takes the new `REVIEWED_SHA` from `build_loop.py --handoff` exactly as §5.1 does, and then re-runs `/code-review`.

Keep the staleness computation (`git rev-list <REVIEWED_SHA>..HEAD --count`) and the operator-override paragraph unchanged. Mirror §5.1's gate phrasing so the two entries read as one rule.

**Patterns to follow:** the §5.1 gate paragraph at `plugins/saga/skills/work/SKILL.md:882-901`; the `repairs_requested` bullet's "passes Phase 3.3 and the 5.1 gate" phrasing.

**Test scenarios:** the executable proof for these lands in U2's test; the implementer confirms each by reading the edited section.

- Stale sentence gone: input the §5.3 text, search for "capturing a fresh"; expected no match (AC-1).
- Routing named: input the stale-paragraph slice (stale opening through `### 5.4`), read it; expected it names Phase 3.3, the combined-branch loop and `build_loop.py --handoff` before re-running `/code-review` (AC-2).
- Staleness computation untouched: input §5.3; expected the `git rev-list <REVIEWED_SHA>..HEAD --count` block is unchanged.

**Verification:** `grep -n "capturing a fresh"` over the skill finds nothing; reading §5.3 shows the stale path going through Phase 3.3 and `--handoff`; no other section changed.

**Functional checks:**

### U2. Regression test and changelog entry

Pin the fixed wording with a failing-first test and record the fix.

**Goal:** A regression test pins the §5.3 stale-review wording, and the changelog records the fix.

**Requirements:** R3, R4, R5.

**Dependencies:** U1.

**Files:** `plugins/saga/tests/test_work_stale_review_gate.py` (create); `plugins/saga/CHANGELOG.md` (modify).

**Approach:** Write the new test mirroring `plugins/saga/tests/test_work_prose_contracts.py`: walk four parents from the test file to the repo root, read the work skill, and slice the stale-review paragraph from its opening through `### 5.4`. Assert "capturing a fresh" is absent from the skill, the stale slice names Phase 3.3 with the combined-branch loop and `build_loop.py --handoff`, and re-running `/code-review` is still instructed. Pin the card's "any other way" clause: fail when `git rev-parse` appears in the slice, or when any `REVIEWED_SHA=` assignment there does not go through `build_loop.py --handoff`. Pin the slice boundary by asserting the repairs-bullet marker is outside it.

Prove red-then-green by running the new test against the pre-U1 text and the fixed text. Add the changelog entry under `## [Unreleased]` and `### Fixed`, referencing issue #144, in the existing entry style.

**Patterns to follow:** `plugins/saga/tests/test_work_prose_contracts.py` for the test shape; the Unreleased Fixed entries in `plugins/saga/CHANGELOG.md` for the changelog line.

**Test scenarios:**

- Happy path: fixed skill text, run the new test file; expected pass.
- Red proof: pre-fix skill text (stash the U1 edit), run the new test file; expected fail, naming the stale paragraph (AC-3).
- Masking guard: the stale-paragraph slice excludes the repairs and cap bullets, so their pre-existing "Phase 3.3" mentions cannot satisfy the routing assertion on broken text.
- No other capture way: a stale slice containing `REVIEWED_SHA=$(git rev-parse HEAD)`; expected fail on both the `git rev-parse` rule and the assignment rule (card's "any other way" clause).
- Suite green: full `plugins/saga/tests` run; expected pass (AC-4).

**Verification:** the focused test passes on the fixed text and fails on the pre-fix text; the changelog carries the Unreleased entry; the full saga suite passes.
