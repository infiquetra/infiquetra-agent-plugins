# A setup command that opens the setup pane directly (issue #221)

## Summary

`/saga:setup` today round-trips through the agent: the agent calls `mcp__saga__setup`, the pane opens, and the answer travels back through the session's output check. This plan registers `/setup-view`, a saga mod command that opens the same setup pane at once — survey, installs and optional steps all run from the pane, the agent stays out of the loop, and the tool path keeps every behaviour #218 tested.

---

## Problem Frame

This is card #221 of the #147 program (saga's code review redesign), asked for by the operator on 11 October so the saga release ships a friendlier setup together with the `outcome-schedule` step the operator installs from it. Today `/saga:setup` loads a skill, the agent calls the `mcp__saga__setup` tool, the tool opens the pane and waits, and the result returns through the agent. That round trip is slow, it depends on the tool result surviving the session's output check (#218 fixed one break there, landed as 491627a), and nothing happens until the agent's turn comes round. The review pane (`/review-view`) and the plan viewer (`/plan-view`) already register their own commands and open their panes directly; setup should work the same way.

The setup pane itself (`plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx`) already draws the survey rows, the install loop and the optional steps with per-row progress. What is missing is the second opener: a slash command registered at session start, answered by a `command.run` hook that surveys and opens without any tool call, and closes without answering one.

---

## Requirements

Requirements are grouped by concern; R-IDs run continuously.

**Command registration**

- R1. The saga mod registers `/setup-view` at session start with `immediate: true`, a name that collides with no saga skill, adapter command, sibling mod command or built-in; running it opens the setup pane with no tool call and no agent turn (AC-1).

**Command-opened pane**

- R2. Opened by the command, the pane runs the survey itself for the session checkout and renders each tool's state and each optional step with its done state; a survey failure renders as a plain message with the script's last lines, never a crash; a step runs from the saga plugin root (AC-1, AC-2).
- R3. Closing the command-opened pane returns nothing to the agent and leaves no pending tool call; while any setup pane is open, neither a second command nor a tool call opens another (AC-1).

**Shared pane behaviour**

- R4. An install or a step started from the pane shows running, then done or failed, per row; a failure shows the last lines of output; the survey refreshes after each action so done states are current (AC-3).
- R5. A failed row offers Ask Claude, which hands the row, the command and the output tail to the session prompt; when the prompt cannot take text the pane says so, and the failure text stays selectable (AC-3).

**Tool path and docs**

- R6. The tool path (`mcp__saga__setup`) keeps every behaviour #218 tested, and both paths share one survey, install and step implementation; the pane points to `/saga:setup` for the repository questions (AC-4, AC-2).
- R7. The setup skill and the saga README name the new command for Claude Code users; the changelog records issue #221 under Unreleased with no version bump (AC-4).

## Key Technical Decisions

Each entry is the decision, then why, naming what was rejected.

- **KTD1. The command is `/setup-view`, registered beside the tool at session start with `immediate: true`.** The name parallels `/review-view` and `/plan-view`, so a Claude Code operator finds it the same way. It collides with none of the 14 saga skills, the 15 adapter command files, the two sibling mod commands, or any built-in — and the engine refuses a built-in's name at registration, so a collision would fail loudly rather than shadow. Registration shares the existing `session.start` hook that registers the tool, keeping the one-matcher-less-slot rule the mod's own comment records. Rejected: `saga-setup` (confusable with the `/saga:setup` skill at a glance); `tool-setup` (less discoverable, breaks the `-view` parallel); a new `session.start` hook (risks the second-registration refusal).
- **KTD2. One pane, two openers.** The command path reuses the pane id, the session atom, the render and the install and step runners; a new `openedBy` field (`'tool'` or `'command'`) on the pane state steers only the close and Done semantics. `active` guards both paths (one setup at a time either way); `outcome` belongs to the tool path only, so the command path can never answer a tool call. The shared-implementation test then falls out of the structure: there is no second survey, install or step implementation to drift. Rejected: a second pane id or a duplicated render (two implementations that drift, violating the card's sharing test on day one).
- **KTD3. `command.run` surveys first, then opens, then returns `{text}` at once — it never waits.** The hook guards an open setup, checks for a terminal or desktop surface, runs the survey for the session checkout through the shared reader, probes the step checkout, opens the pane and returns text naming what opened. A survey failure still opens the pane, carrying a `surveyError` the render draws as a plain message with the script's last lines; the card's "renders … never a crash" wants the pane up, not a bare text answer. An empty survey (no tools, no steps), an undrawable surface and an unplaceable pane answer as text and open nothing, mirroring the tool path's nothing-to-review, unavailable and not-placed. Rejected: waiting on the sleep loop like the tool path (there is no tool call to answer, so a wait would only hold the command); returning text without opening on survey failure (hides the tail the operator needs).
- **KTD4. Refresh and Ask Claude live in the shared runners and rows, so both paths get them.** After an Install run ends and after each step settles, the runner re-reads the survey; on success the pane swaps in the fresh survey while keeping the operator's ticks for surviving rows, and on failure it toasts and keeps the shown survey. Ask Claude is `$.prompt.fill` with mode `insert`, carrying the row id, the command as run and the output tail — the same call the Quote buttons already make — with the same toast when the prompt reports `isFilled: false`; failure lines stay plain text, which the operator can select. The card's "when the build exposes a way" conditional is resolved at plan time: `$.prompt.fill` exists on the floor build and is proven by the siblings' tests, so no fallback branch ships. Rejected: `$.prompt.submit` (it would run the agent unasked, against the card's "agent stays out of the loop"); replacing the operator's ticks on refresh (a re-survey must not untick what the operator chose).
- **KTD5. The tool path stays byte-identical in behaviour.** Same survey, install and step argv, same statuses through `paneResult`, same offer, same Done lists (installs only — steps never join them). The #218 setup-pane tests run unmodified and green; the refresh only adds survey calls the stubs already answer, and no #218 assertion counts survey calls. Rejected: re-surveying before Done submits (Done reports the run the operator watched, not a later state); touching the offer toast (it names `/saga:setup`, which is still where the repository questions live).

## Implementation Units

Three units: the command and its pane, the shared refresh and Ask Claude behaviour, then the skill, README and changelog.

### U1. The setup-view command and its pane

A slash command that surveys and opens the setup pane with no tool call, and closes without answering one.

**Goal:** `/setup-view` is registered at session start and opens the setup pane through a `command.run` hook; the command-opened pane surveys, renders, runs steps from the plugin root, and closes leaving nothing pending.

**Requirements:** R1, R2, R3.

**Dependencies:** none.

**Files:** `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx` (modify: command registration, the `command.run` hook, the `openedBy` close semantics, the survey-error render); `plugins/saga/com.infiquetra.claude/types/index.d.ts` (modify: `openedBy` and `surveyError` on `SagaSetupReview` beside `:530-539`); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx` (modify: the command tests).

**Approach:** Register `{name: 'setup-view', description, immediate: true}` in the existing `session.start` hook right after the tool registration (KTD1). Answer with `on('command.run', {command: 'setup-view'})` following the review pane's `openReviewView` shape: when a setup is active, answer text naming that one is already open; with no terminal or desktop surface, answer the unavailable text and open nothing; otherwise run the shared survey reader with the session checkout as repo, probe the step checkout through the shared exists probe, and open the pane with `focus: true`. A survey failure opens the pane carrying `surveyError` (KTD3); an empty survey answers "nothing to set up" as text and opens nothing; an unplaceable pane answers the not-placed text. Return `{text}` immediately in every case — no sleep loop. The render draws `surveyError` as a plain message with the script's last lines plus a Close button, before any survey read, so it cannot crash. The action row branches on `openedBy`: command mode shows a single Close (Done and Dismiss promise an answer to someone, and nobody waits here); tool mode keeps today's buttons. Close, and the window close or Escape through the `ui.close` handler, run one shared cleanup — `active` false, both epochs bumped so orphaned loops can never mark another setup, pane closed, state cleared — and never touch `outcome` (KTD2).

**Patterns to follow:** `plugins/saga/com.infiquetra.claude/mods/review-pane.tsx:152-157` (command registration at session start) and `:175-178` (the `command.run` hook answering `{text}`); `plugins/saga/com.infiquetra.claude/mods/plan-viewer.test.tsx:150-157` (driving `$.command.run` with origin and presentation) and `:137-141` (stubbing `prompt.fill`); `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx:208-212` (the `ui.close` handler this extends) and `:150-206` (the tool-call guards the hook mirrors).

**Test scenarios:**

- Happy path: session start records the registration with name `setup-view` and `immediate: true`; the name differs from every saga skill name, every adapter command file stem, `plan-view` and `review-view` (pinned list in the test; built-ins are refused by the engine itself). `$.command.run({command: 'setup-view', ...})` opens the pane, runs the survey argv with `--repo` set to the session checkout, records no `mcp__saga__setup` tool call, and resolves text naming the opened survey.
- Survey failure: a survey exiting 2 with stderr opens the pane showing the plain message and the script's last lines, with a Close button and no crash; the command text names the failure.
- Empty survey: no tools and no steps answers text and opens no pane.
- Close: pressing Close resolves nothing further (the command already answered), clears `active` and the state, so a second command opens a fresh pane.
- Guards: the command while a tool-opened pane is up answers "already open" text and opens nothing; a tool call while a command-opened pane is up returns the existing already-open error string.
- Undrawable and unplaceable: a mobile-only surface answers the unavailable text with no open; a refused placement answers the not-placed text.
- Window close: closing the command-opened pane as the person does (the closer-plugin pattern) clears `active` and the state, and a later tool call proceeds normally.

**Verification:** the suite and the registration pin below pass; then the live proof AC-1 needs: start Claude Code 2.1.296 with `CLAUDE_CONFIG_DIR` at a scratch folder and `--plugin-dir` at this worktree, in a NEW Herdr tab of the card workspace (never split a pane), type `/setup-view`, and confirm the pane opens before any agent turn, with no collision in the typeahead. Never press Run on a step in the live session (it installs on the operator's machine); prove installs and steps with the stubbed tests. Record the per-criterion outcome in `.program/acceptance.md` and delete the scratch folder after.

### U2. Shared refresh, Ask Claude, and the skill pointer

Every install and step refreshes the survey when it settles, failures offer Ask Claude, and the pane points at the skill for the repository questions.

**Goal:** The shared runners re-survey after each action, failed rows offer Ask Claude through the session prompt, and the pane names `/saga:setup` for the repository questions — in both open modes, with the #218 tool-path tests green unchanged.

**Requirements:** R4, R5, R6.

**Dependencies:** U1 (the `openedBy` state and command mode this behaviour also serves).

**Files:** `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx` (modify: refresh in the install loop and step runner, the Ask Claude buttons, the `/saga:setup` pointer line); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx` (modify: refresh, Ask Claude and pointer tests). `run-record.ts` and `run-record.test.ts` need no change: every verb the command path runs — survey, install, step, the exists probe — already has its shared reader or argv builder there, which the card's file list was written before verifying.

**Approach:** After the Install loop ends (all done, first failure, or throw) and after each step run settles, re-read the survey through `readSetupSurveyWith`, under the same epoch guard as the runner so a late answer can never mark another setup. On success swap in the fresh survey, keeping the operator's ticks for surviving rows, seeding new rows from `initialTicks`, and dropping vanished ones; progress maps stay. On failure toast the reason and keep the shown survey (KTD4). Beside each failed install row and failed step, offer an Ask Claude button that calls `$.prompt.fill({text, mode: 'insert'})` with the row id, the command as run (the argv joined) and the shown output tail; when the prompt answers `isFilled: false`, toast that it cannot take text. Failure lines stay plain text so the operator can select and paste them. Add one dim line naming `/saga:setup` for the repository questions the skill asks. All of this lives in the one render and its runners, so the tool path and the command path share it with no second implementation (KTD2, KTD5).

**Patterns to follow:** `plugins/saga/com.infiquetra.claude/mods/review-pane.tsx:105-108` and `plugins/saga/com.infiquetra.claude/mods/plan-viewer.tsx:108-111` (fillPrompt with the cannot-take-text toast); `plugins/saga/com.infiquetra.claude/mods/setup-pane.tsx:245-302` (the guarded install loop and step runner the refresh extends); `plugins/saga/com.infiquetra.claude/mods/setup-pane.test.tsx:85-162` (the world stubs, extended with a second-survey answer and a `prompt.fill` hook).

**Test scenarios:**

- Happy path: after an Install run, the pane re-surveys and a row the second survey reports installed renders installed; the operator's ticks on surviving rows are unchanged.
- Step refresh: after a step settles, the second survey's flipped done state renders; a re-run still offers Run.
- Refresh failure: a re-survey exiting non-zero toasts the reason and keeps the shown survey, ticks and progress.
- Ask Claude on an install failure: the failed row offers the button; pressing it fills the prompt with text containing the row id, the install command and the output tail; with `isFilled: false` the pane toasts instead and the failure text remains on screen, selectable.
- Ask Claude on a step failure: same shape, with the step command; one case runs in the tool-opened pane and one in the command-opened pane.
- Pointer: the command-opened pane shows the `/saga:setup` line for the repository questions.
- Tool path kept: every #218 setup-pane test (submitted, dismissed, timed-out, steps, empty-installable, offer) runs unmodified and green.

**Verification:** the suite and the pins below pass, with the #218 tool-path tests untouched in the run.

Later (noted here, never a unit of this plan):
